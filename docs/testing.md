# テスト方針

## レイヤーの分け方

テストは「どのファイルのテストか」ではなく、速度、つまり回せる頻度で分ける。
TDD の赤→緑ループは `unit` だけを watch で回し、`integration` / `e2e` はコミット前に通す。

| 層            | 置き場所            | 性質                                               | 目安         |
| ------------- | ------------------- | -------------------------------------------------- | ------------ |
| `unit`        | `test/unit/`        | I/O なし。純粋な関数とインメモリの状態遷移         | 数ms         |
| `integration` | `test/integration/` | 一時プロジェクト or dev サーバー1つ                | 数十〜数百ms |
| `e2e`         | `test/e2e/`         | `build()` / `createTestBuilder()` 経由のフルビルド | 1件 ~1s      |

```bash
npm run test:watch    # unit だけを watch（TDD 用）
npm run test:unit
npm run test:integration
npm run test:e2e
npm test              # 全部（コミット前）
```

## 書き方の指針

### 1テスト = 1つの仕様文

テスト名は README / architecture.md の記述をそのまま引用できる粒度にする
（例:「dev は outDir に一切書き込まない」）。

### 内部プロパティを見ない

バイト数カウンタのような実装の内部ではなく、
「上限を超えたら古いものが消える」という観測可能な振る舞いで検証する。

内部を見たくなったら、それは公開 API が足りないサイン。
SSE の接続数を確かめたくなったので `context.server.clientCount` を足した、など。

### 「無いこと」を確かめるテストは、前提が成立しているかも確かめる

`not.toContain` や `toEqual([])` は、そもそも対象が処理されていなくても通ってしまう。

パストラバーサルのテストで `../` の数が固定されており、対象ファイルに届いていなかった。
配信ルートからの相対パスを計算し、「届くはずのパスであること」を先に assert した。

「`_` 始まりの画像を出力しない」の fixture に画像が 1 枚も無く、`No images found` で素通りしていた。
実画像を置き、「対象の画像が実際に処理されていること」を先に assert した。

どちらも実装の除外規則を外しても緑のままだった。疑わしいときはミューテーションで確かめる。

### 出力を探す目印は、後処理が書き換えない値にする

CSS は dev でも Lightning CSS を通るので、書いた文字列がそのまま出るとは限らない。
色は短い表記に正規化され（`rebeccapurple` は `#639`）、その属性の初期値にあたる
キーワードは `initial` になる。圧縮していなくても起きる。

目印にはセレクタ名や `7px` のような、正規化されない値を選ぶ。
色名を目印にした差分ビルドのテストは、これで通らなくなった
（`test/integration/dev-startup.test.mjs`）。

同じことは HTML 整形にもあてはまる。観測点は「通り道が値を変えないもの」から選ぶ。

### 一時プロジェクトは createTempProject() を使う

`test/helpers/project.mjs` にある。
リポジトリ内への書き出し・実在しないパスへの `fs` 操作・`process.cwd()` 依存を構造的に防ぐ。
後始末は `onTestFinished` で自動的に行われる。

```js
const project = await createTempProject({
  'src/index.pug': 'p home\n'
})
```

### ビルダーは createTestBuilder() を使う

`createBuilder()` を直接呼ばない。

常駐リソース（Sass のコンパイラプロセス・esbuild のビルドコンテキスト）は
`BuildContext` 単位で持つので、`close()` しないとテストごとに積み上がる。
`watcher.stop()` や `context.server.close()` では解放されない。

```js
const builder = await createTestBuilder(project.root, 'development')
// onTestFinished で close() が登録される
```

実際に呼び忘れが積み上がっていた実例は
[ADR 0007](adr/0007-resources-live-in-context.md) の結果にある。

`FileWatcher` を直接組み立てる場合は、監視の停止だけ別に登録する。
`builder.watch()` を通していないと `builder.close()` は watcher を知らない。

### 偽の context は、その関数が context の一部しか触らない場合だけ

出力先の削除を伴う処理（unlink 系）に実在しないパスを渡すと、
そのパスが存在する環境でユーザーのファイルを消す。必ず一時プロジェクトを使う。

### 並行性は sleep で待たない

自分たちのコードの並行性は、関数注入と Deferred で決定論的に制御する
（`test/unit/lazy-page-builder.test.mjs` が見本）。

例外は 2 つある。どちらも「こちらから制御できない外部の都合」で、
決定論的な合図が取れない場合に限る。

外部が発する事象の待ち。chokidar の初期走査や、切断したソケットが
サーバー側に伝わるまでがこれにあたる（`test/integration/dev-startup.test.mjs`、
`test/integration/server-http.test.mjs`）。合図が取れるものは合図を使う。
chokidar の `ready` イベントは取れるので、そちらを優先する。

ファイルシステムの mtime の解像度。書き込みの前後で mtime を比べるには
数ミリ秒空ける必要がある。これは待ち合わせではなく単位の問題。

### 待ち上限を自前で持つなら、vitest 側の上限より短くする

vitest の既定は 20 秒（`vitest.config.mjs` の `testTimeout`）。

内部の上限をそれより長くしても、vitest が先に打ち切るので伸ばした意味がなく、
しかも「終わらなかった」のか「遅かっただけ」なのかが区別できない失敗になる。

伸ばすときは `it(name, fn, timeout)` で両方を上げる
（`test/e2e/dev-shutdown.test.mjs` が見本）。

### dev サーバーは server.port = 0 で起動する

OS がポートを割り当てるので並列実行でも衝突しない
（`test/integration/server-http.test.mjs` が見本）。

`FileWatcher.start()` もキャッシュを消す前にポートの空きを確認するため、
watcher を直接動かすテストでも 0 を指定する。

### 「作り直されたか」は内容ではなく mtime で観測する

内容の一致だけを見ると、差分ビルドが全ビルドに退行しても気づけない。

## TDD の進め方

外から1本、そのあと中を単体で。pugkit は「タスクの合成」が設計の本体なので、
部品を下から積むと「全部緑なのに繋ぐと動かない」事故を起こす。

1. `e2e` に赤いテストを1本書く（最終的にどう出力されてほしいか）
2. それを緑にするのに必要な純粋関数を `unit` で TDD する
3. 設定の受け渡しがあるなら `integration` に1本足す
4. dev と build で経路が分かれるものだけ、パリティのテストを `e2e` に足す

ステップ4は経路が分かれる場合に限る。dev と build が同じ関数を通る機能に
パリティテストを書いても、原理的に落ちないテストが増えるだけになる。

### 終了コードは子プロセスで叩かないと守れない

公開 API はプロセスを終わらせない。終わらせると、テストから呼んだ瞬間に
vitest ごと落ちる。そのため終了コードを決めるのは `cli/` だけになり、
公開 API を呼ぶテストではそこが 1 行も実行されない。

`pugkit check` は当初この状態で、報告の整形も終了コードも無検査のまま通っていた。
`execFile` で CLI を起動して確かめる
（`test/integration/check-cli.test.mjs` が見本）。

同じ理由で、CLI にしか無い分岐も子プロセスから見る。知らないサブコマンドを
弾く判定は `cli/index.mjs` にあり、公開 API からは辿れない。

## テストが仕様を守っているかを確かめる

テストを足したら、その仕様をわざと壊してテストが赤くなるかを確認する。
赤くならないなら、そのテストは何も守っていない。

```bash
# 例: 差分ビルドを全ビルドに退行させてテストが落ちるか
# → 落ちなければ「差分であること」を観測できていない
```

実際にこの方法で、`computeMorphSignature` の `<html>` 属性・`<script>` 検出、
`buildPageHtml` の依存グラフ書き戻し防止、`clean` の削除範囲、dev の差分ビルド、
配信ルートの封じ込め、非 Pug HTML へのライブリロード注入、SSE の後始末が
「テストがあるのに守られていない」状態だと分かった。

`REBUILD_SPECS` を表に切り出したときも、`root` キーを落とす、`label` を誤記する、の
2 通りを実際に壊して、それぞれ別のテストが落ちることを確認してから採用した。
表に切り出した設定値は、例外にならない間違い方をするので、この確認を省かない。

### 判定は落ちたテストの名前で見る

件数だけ見ない。ミューテーションによって落ちるテストが入れ替わり、
件数が同じになることがある。

### バグ修正は「再現テスト、そのあと修正」の順で行う

先にテストを書けば、直したつもりで直っていない状態を検出できる。
`_` 始まりディレクトリがスタイル・スクリプトのビルド対象に入っていた不具合は、
この順序で発見・修正した。

## 何をテストしないか

定数がその値であること（`defaults.mjs` の値そのもの）。
変更は常に意図的で、テストは「変えたことを知らせる」以上のことをしない。
守るべきはマージ規則の方。

ログ出力の文言。言い回しを変えたら落ちるテストは、変更のたびに直すだけで何も守らない。

どこからも呼ばれていないコード。テストを足すのではなく削除する。

他のライブラリの出力そのもの。Lightning CSS の圧縮結果や js-beautify の整形結果は
向こうの仕様で、こちらが守るものではない。見るのは「その設定で出た結果が要件を満たすか」で、
対象ブラウザを変えたときにプレフィックスと降格が付いてくるか、が観測点になる
（`test/integration/task-sass.test.mjs`）。

### 例外: 識別子がそのまま利用者に出る場合

`core/watcher.mjs` の `REBUILD_SPECS` は、表のキーがログの接頭辞を兼ねている
（`image: assets/img/hero.jpg`）。

キーはデータ構造の識別子でもあるので、リネームすると利用者に見える表示が黙って変わる。
さらに `root` キーの有無は表示されるパスそのものを変える。

ログが唯一の観測点なので、そこだけは文言で固定する。
守っているのは言い回しではなく「どの基準で相対パスを出すか」という規則。
