# 0004. dev のキャッシュは永続化しない

## 状況

dev は起動のたびに `cacheDir` の中身を削除して作り直す。
そのため毎回、CSS・JS・画像・SVG・スプライト・public を全部作り直している
（`core/dev/startup.mjs` の `INITIAL_DEV_TASKS`）。

残しておけば起動が速くなるはずで、実際 Vite は `.vite`、Next は `.next/cache` を残す。

## 決定

`cacheDir` は起動のたびに作り直す。前回セッションの生成物は再利用しない。

## 理由

再利用するには「この出力が今のソースと対応しているか」を起動時に判断する必要がある。
pugkit はハッシュも mtime もマニフェストも永続化していないため、判断する材料が無い。

材料が無いまま残すと、次のすべてが無警告で起きる。

dev を止めている間にソースを削除した場合、消したはずのファイルが配信され続ける。

dev を止めている間にソースを編集した場合、ウォッチャーが動いていないので無効化されず、
古い出力がそのまま配信される。エラーも警告も出ない。

`imageOptimization` を webp から avif に変えた場合、全画像が古い形式のまま残る。

pugkit 自体を更新した場合、sharp の設定やスプライトの形式が変わっていても、
前バージョンの出力が混ざる。

いずれも「なぜか古いものが出る」という形で現れ、原因に辿り着きにくい。

## 得られるはずだった速度

1600x1200 の写真 40 枚（`imageSourceDensity: 2` なので出力 80 枚）で計測した。

| 条件             | dev 起動完了まで       |
| ---------------- | ---------------------- |
| 画像 40 枚       | 3,827 / 4,083 ms       |
| 画像 0 枚        | 2,408 ms               |
| 画像の処理コスト | 約 1.5 秒（1 枚 37ms） |

残る 2.4 秒は Node の起動と sharp・esbuild・sass-embedded の読み込みで、
キャッシュを残しても縮まない。

つまり 40 枚で 1.5 秒、400 枚で 15 秒程度の話になる。

## 却下した案

### ソースのハッシュを記録したマニフェストを持つ

出力ごとに入力のハッシュを保存し、一致すれば再利用する。
設定の変更と pugkit のバージョンでも無効化する。

正しく作れるが、失敗したときの現れ方が無言になる。
上に挙げた 1.5 秒のために、静かに壊れる仕組みを 1 つ増やすことになる。

前提が変わるとすれば、点数の多い案件で起動時間が実際に問題になったときだが、
その場合の答えは次の案の方が良い。

### 画像もリクエスト時生成に移す（保留）

HTML と同じく、要求された時点で生成する。

起動時の画像処理が 0 になるので、キャッシュ永続化より効果が大きい。
かつ現在のソースから生成するため、陳腐化が原理的に起きない。

現時点で起動時間が問題になっていないため保留している。
`docs/todo.md` に記録済み。

## 結果

`cacheDir` に指定したディレクトリは、dev 起動のたびに中身が削除される。
既存ファイルのある場所を指定してはいけない。

事故を防ぐため、削除の前に二段で確認する。

pugkit が作ったディレクトリであることを目印ファイル `.pugkit-dev-cache` で確認する。
目印が無いのに中身がある場合は中止する。

目印に記録された持ち主の PID が生きている場合、別の dev サーバーが使用中と見なして中止する。
ポートの空き確認では守れない。ポートを変えれば 2 つ目が起動できてしまい、
判定するものと壊すものが対応しないため、守る対象そのものに持ち主を持たせている。
