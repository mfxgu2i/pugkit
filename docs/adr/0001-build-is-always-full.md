# 0001. build は毎回フルビルドする

## 状況

ビルドツールは差分ビルドで速くするのが普通で、pugkit も当初はハッシュキャッシュを持っていた。

しかし静的サイトの本番ビルドは CI かデプロイ直前に 1 回走るだけで、
待ち時間が数秒縮んでも得るものが少ない。
一方で差分判定を間違えると、古いファイルが本番に混ざる。

## 決定

`pugkit build` は変更検知をせず、対象ファイルをすべて処理する。
ビルド成果物のキャッシュは保存も参照もしない。出力ディレクトリは開始前に削除して作り直す。

ソースが変わらなければ結果も変わらない読み取り結果（画像の実寸）は例外とし、
1 回のビルドの中では再利用する。複数のページから同じ画像を参照したときに
同じファイルを何度も開かないためで、ビルドをまたいでは持ち越さない。

内容が変わっていないファイルも必ず書き出す。

## 理由

差分ビルドの誤りは、成果物を見ても気づけない。
「なぜか古い CSS が本番に出ている」という形で、デプロイ後に発覚する。

毎回全部作れば、出力は入力だけで決まる。
同じソースからは必ず同じ出力が出るので、再現しない不具合が起きない。

dev の応答性は別の手段（0002）で確保しているため、build を速くする動機がそもそも弱い。

## 却下した案

### 内容ハッシュによる差分書き込み

書き込み前に既存ファイルとハッシュを比較し、同じならスキップする。

出力ディレクトリを削除しない前提になるため、ソースから消したファイルが
出力に残り続ける問題を別途解こうとする必要が出る。得られるのは書き込み時間だけで、
変換そのもの（sharp・sass・esbuild）の時間は縮まない。

### mtime による差分判定

チェックアウトや `git checkout` で mtime が変わるため、CI では毎回全ビルドになる。
ローカルでだけ効く仕組みは、挙動が環境で変わるので避けた。

## 結果

`outDir` は pugkit が占有する。手で置いたファイルは build のたびに消えるため、
出力に含めたいものは `public/` へ置く必要がある。

作り直しを止める `build.clean` オプションは廃止した。破壊的変更にあたる。
設定に残っていても無視される。

既存サイトへ組み込む場合は、`outDir` を専用のディレクトリにしてデプロイ時に配置する。
