# 0007. 常駐リソースは BuildContext が持つ

## 状況

Sass のコンパイラプロセスと esbuild のビルドコンテキストは、作るのが高くつくので
dev のセッション中は使い回したい。

当初はモジュール変数に置いていた。
そのためプロセス全体で 1 つになり、同じプロセスで 2 つ目のビルダーを作ると
互いのリソースを奪い合う。片方の `close()` が、もう片方が使っている常駐プロセスを落とす。

画像の寸法キャッシュも同じ形で、`clearImageSizeCache()` がプロセス全体に効いていた。

また `Builder.close()` が停止のために `tasks/sass.mjs` と `tasks/script.mjs` を
名指しで動的 import しており、core が個別のタスクを知っている状態だった。

## 決定

常駐リソースは `BuildContext` が持つ（`context.resources` / `core/resources.mjs`）。
寿命はセッションと同じになる。

作り方はタスク側が渡し、捨て方はリソース自身が `dispose()` で持つ。
`Builder.close()` は `resources.disposeAll()` を呼ぶだけで、中身を知らない。

画像の寸法キャッシュは `CacheManager.imageSizes` に移し、他のキャッシュと揃えた。

## 理由

1 プロセスに 1 ビルダーという暗黙の前提が消える。
テストを並列に走らせても、組み込んで複数のビルダーを作っても、互いに干渉しない。

core がどのタスクの事情も知らなくなるので、常駐プロセスを持つタスクが増えても
`Builder` を触らずに済む。

## 却下した案

### BuildContext に名前付きのフィールドを持たせる

`context.sassCompiler` のように直接持たせる方法。

core が「どのタスクが何を抱えているか」を再び知ることになり、
名指しの動的 import を消した意味が薄れる。

### タスク登録時に dispose を渡す

`registerTask(name, { run, dispose })` の形。一度これを実装した。

リソースの置き場が別に必要になるため、結局二重の仕組みになる。
`ResourceStore` が寿命を持てば `dispose` の受け渡しは要らないので、後に畳んだ。

## 結果

`close()` が必須になった。呼ばないとセッションごとに常駐プロセスが積み上がる。

以前はモジュール変数で共有していたため、`close()` を忘れても
プロセス全体で 1 つに収まっていた。この保護が無くなった。

実際にテストの 18 箇所が `close()` を呼んでおらず、2 ファイルを走らせるだけで
常駐プロセスが 4 個から 19 個に増えていた。テストは全部緑のまま、
プロセス数を実測して初めて分かった。

テストからは `createTestBuilder()` を使い、`onTestFinished` で必ず閉じる
（`docs/testing.md` に記載）。
