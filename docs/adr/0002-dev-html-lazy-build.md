# 0002. dev の HTML はリクエスト時に作る

## 状況

共通レイアウトを 1 文字直すと、全ページを作り直すことになる。
ページ数に比例して待ち時間が伸びるため、規模の大きい案件ほど dev が使いにくくなる。

実際には、編集中に見ているのはブラウザで開いている 1 ページだけであることが多い。

## 決定

ウォッチャーは変更を検知してもビルドしない。
キャッシュの無効化とリロード通知だけを行う。

HTML はブラウザがそのページを要求した時点で 1 ページ分だけ生成し、
ファイルに書かずメモリから配信する。

## 理由

編集から画面に反映されるまでの時間が、プロジェクトのページ数に依存しなくなる。
共有パーシャルを直しても、体感は 1 ページ分のビルド時間になる。

書き出さないので、ディスクへの書き込み完了を待つ必要もない。

## 却下した案

### 変更されたページだけを事前ビルドする

依存グラフから影響ページを割り出して、そこだけ作り直す。

グラフを正確に保つ必要があり、include の追加や削除で取りこぼすと
「直したのに反映されない」が起きる。またページ数が多いと、影響範囲が広い
パーシャル（レイアウトなど）を直したときに結局全ビルドと変わらない。

## 結果

依存グラフはページが最初に要求されてコンパイルされた時に作られる。
未訪問のページはキャッシュに無いため、次の要求で最新のソースから作られる。
キャッシュにあるページには必ずグラフの辺が存在するので、無効化は正確に行える。

ビルド中に無効化が入った場合に古い結果を書き戻さないよう、
ページ単位の世代（epoch）で管理する。

同じページへの同時要求は 1 回のビルドにまとめる（`core/dev/lazy-builder.mjs`）。

メモリが際限なく増えないよう、ページ HTML のキャッシュには 64MB の上限を置き、
超えた分は古い順に捨てる。捨てられたページは次の要求で作り直されるだけなので、
正しさには影響しない。

ビルドに失敗した場合は、エラー内容とライブリロードスクリプトを載せた 500 ページを返す。
エラーはキャッシュしないので、ソースを直して保存すれば自動で復帰する。
