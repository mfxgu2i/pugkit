# 0009. HTML の整形は js-beautify の既定に寄せる

## 状況

pugkit は生成した HTML を js-beautify で整形する。既定値のうち 2 つが、
納品する HTML として困る形になっていた。

`inline: []` は、js-beautify が持つインライン要素の一覧を空にする。
結果としてインライン要素が改行され、そこに空白が生まれる。

```
入力  <ul><li><a href="#">A</a></li></ul>

出力  <ul>
        <li>
          <a href="#">A</a>
        </li>
      </ul>
```

HTML では改行と字下げが 1 個の空白に潰れる。`li` や `a` を `inline-block` で
詰めて並べると、ソースには書いていない隙間が入る。

`content_unformatted: ['script', 'style', 'pre']` は js-beautify の既定から
`textarea` を落としている。textarea の中身は表示される値そのものなので、
整形すると値が変わる。

```
入力  <textarea>\n  keep\n</textarea>
出力  <textarea> keep </textarea>
```

どちらも例外にならず、ブラウザで開くまで気づけない。

## 決定

`inline` を上書きしない。js-beautify の既定の一覧をそのまま使う。

`content_unformatted` に `textarea` を戻す。`['script', 'style', 'pre', 'textarea']`
とし、pugkit が足すのは `script` と `style` だけにする。

既定値を上書きするのは、既定のままでは困るものに絞る。

## 理由

pugkit が掲げているのは「納品向きの綺麗な HTML」で、表示を変えない整形が前提になる。
インライン要素の間に空白を入れる整形は、綺麗かどうか以前に別の HTML になっている。

js-beautify のインライン要素の一覧は仕様の写しであり、pugkit が持ち直す理由が無い。
上書きしていたのは、要素の性質を判定に使わせない意図があったからではなく、
既定の内容を確かめずに空で埋めたためと見られる。

`script` と `style` を残したのは、中身を別の整形器に通す挙動を避けるため。
バンドル済みの JS や CSS を Pug に埋め込む使い方があり、そこを触ると
minify 済みの内容が展開される。

## 却下した案

### `content_unformatted` も js-beautify の既定に完全に合わせる

`['pre', 'textarea']` にすると、`script` と `style` の中身が整形される。
表示は変わらないが、埋め込んだバンドルが展開されて出力が膨らむ。
既定に寄せる理由は「表示を変えないため」なので、ここまで揃える必要は無い。

### 整形そのものをやめる

Pug の出力をそのまま書き出せば、整形に由来する事故は起きない。

納品物として読めない HTML になる。CMS のテンプレートに組み込む前提なので、
人が触る形であることは要件のうちに入る。

### `inline` を pugkit 側で書き下す

必要な要素だけを明示できる。

仕様の写しを二重に持つことになり、HTML の要素が増えたときに追随できない。
js-beautify の更新で直る問題を、こちらが抱え込むことになる。

## 結果

既存プロジェクトの出力 HTML が変わる。差分はインライン要素の改行位置と、
textarea の中身に出る。表示は変わらないか、隙間が消える方向に変わる。

`build.html` で `inline: []` を明示すれば以前の挙動に戻せる。
戻す理由は無いはずだが、整形結果を前提にした差分検証を持つ現場のために口は残る。

既定値を変えても壊れたことが分からない変更なので、
「その設定で出た HTML が表示を変えないか」をテストで固定する
（`test/unit/format-html.test.mjs`）。
