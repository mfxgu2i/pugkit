# 0010. CSS の後処理を Lightning CSS に一本化する

## 状況

Sass がコンパイルした CSS を、PostCSS で autoprefixer と cssnano に通していた。

この構成には穴があった。autoprefixer はベンダープレフィックスを付けるだけで、構文を降ろさない。
対象ブラウザが未対応のモダン構文を書いても素通りし、そのブラウザでだけスタイルが効かない。

```css
/* 対象に未対応ブラウザが含まれていても、そのまま出ていた */
text-decoration-color: oklch(from #ff0 l c h/.5);
```

例外にならず、その環境で開くまで気づけない。

実案件のCSSで測ったところ、後処理の速度も無視できなかった。
Sass 出力 245KB に対して、後処理が build で 158ms、dev で 54ms かかっており、
CSS ビルド全体の 46% を占めていた。

## 決定

CSS の後処理を Lightning CSS に置き換える。PostCSS・autoprefixer・cssnano を依存から外す。

対象ブラウザは browserslist から読む。pugkit は独自の設定項目を持たない。

利用者に PostCSS プラグインの口は開けない。

## 理由

プレフィックスの付与と構文の降格は、どちらも「対象ブラウザが何に対応しているか」という
同じ知識から出る。別々の道具に分けると、片方だけが対象を見ている状態になる。
実際そうなっていて、穴はそこから開いていた。

browserslist に一本化したのは、`.browserslistrc` と `package.json` の両方を
同じ規則で読むため。pugkit が独自の設定項目を持つと、CSS 以外の道具が見ている
対象ブラウザとずれる。

プラグインの口を開けないのは、開けた瞬間に「どのプラグインを通したか」で
出力が変わり、pugkit が出力の性質を保証できなくなるため。
そもそも pugkit は autoprefixer と cssnano しか使っておらず、
利用者にプラグインを渡す口は元から無かった。

## 実測

zerosoft の案件で測った。SCSS 60 ファイル、Sass 出力 245,062 bytes。

| 項目           | PostCSS の構成 | Lightning CSS |
| -------------- | -------------- | ------------- |
| 出力サイズ     | 225,111 bytes  | 214,802 bytes |
| build の後処理 | 158 ms         | 6 ms          |
| dev の後処理   | 54 ms          | 6 ms          |

宣言 4,583 個のうち、値が違ったのは 152 個。大半は等価な正規化で、
`0.2s` が `.2s` に、`normal` がその属性の初期値である `initial` に、
システムカラーのキーワードが小文字になる、といったもの。

ベンダープレフィックスは対象ブラウザの判断で増減が両方向にあった。
autoprefixer が付ける `-moz-tab-size` を Lightning CSS は付けず、
`-webkit-text-decoration-skip-ink` は Lightning CSS だけが付けた。

## 却下した案

### 設定でどちらかを選べるようにする

移行のリスクを下げられる。既存案件の出力を変えずに済む。

engine が2つあると、出力の性質を2通り保証することになる。テストも2通り要る。
pugkit は納品する HTML と CSS の性質を売りにしているので、
「設定によってどちらか」は看板を薄める。v2 は新規案件にだけ使う前提なので、
移行のリスクを下げる理由がそもそも小さい。

### PostCSS に postcss-preset-env を足して降格も担わせる

いまの構成を保ったまま穴だけ塞げる。

依存とプラグインの数が増え、速度は改善しない。
Lightning CSS は同じ仕事を1つの依存で、26 倍速く行う。

### Sass をやめて Lightning CSS のネスティングとバンドルに寄せる

依存が1つ減り、CSS の処理系が1つになる。

Sass の変数・mixin・関数・`@use` による名前空間は、
素の CSS では置き換えられない。既存案件の資産がそのまま動かなくなる。
Lightning CSS は Sass の代替ではない。

## 結果

`.scss` の書き方は変わらない。`@use` / `@forward`・変数・mixin・関数・入れ子は
すべて Sass の担当で、Lightning CSS が受け取るのは Sass が出した平らな CSS になる。

出力される CSS は変わる。既存案件をそのまま v2 に載せると差分が出る。

dev でも色が短い表記に正規化される。`rebeccapurple` は `#639` になる。
圧縮していなくても起きるので、dev の出力で色名を目印にしていたテストは通らなくなる
（`test/integration/dev-startup.test.mjs` の差分ビルドのテストがそうだった）。

手書きのフォールバック宣言を「対象ブラウザには不要」と判断して消すことがある。
実案件では 4 箇所あった。

`lightningcss` はネイティブモジュールなので、インストール時にプラットフォーム別の
バイナリを取得する。sharp と同じ性質で、依存としては既に前例がある。
