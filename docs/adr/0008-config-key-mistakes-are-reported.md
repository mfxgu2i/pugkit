# 0008. 設定キーの誤りを知らせる

## 状況

`pugkit.config.mjs` のキーは、綴りを間違えても素通りする。

```js
build: {
  imageOptimizatoin: 'compress' // 効かない。既定の webp で出力される
}
```

例外にならず、ビルドは成功する。出力を 1 枚ずつ開いて形式を確かめない限り
気づけない。`imageOptimization` の値の検証は入れたが、キー名は見ていなかった。

v2 で画像まわりのキーを `build.image` にまとめたため、この形の誤りが一気に増える。
v1 の設定ファイルをそのまま持ち込むと、5 つのキーすべてが無視される。

| v1                         | v2                               |
| -------------------------- | -------------------------------- |
| `build.imageOptimization`  | `build.image.format`             |
| `build.imageSourceDensity` | `build.image.sourceDensity`      |
| `build.imageOptions`       | `build.image.options`            |
| `build.imageOverrides`     | `build.image.overrides`          |
| `build.imageInfo`          | `build.image.artDirectionSuffix` |

## 決定

設定ファイルのキーを既定値の形と突き合わせ、2 通りに分けて扱う。

旧名のキーは中止する。実在しないキーは警告して既定値で続ける。

有効なキーの一覧は `config/defaults.mjs` の形から導く。表を別に持たない。

## 理由

扱いを分けたのは、直し方が分かるかどうかが違うため。

旧名のキーは移行先が一意に決まる。中止して対応表を見せれば、その場で直せる。
放置すると「compress を指定したのに webp で出る」という食い違いが黙って続く。
指定した値が効かないまま出力されるので、警告では取りこぼしが出る。

実在しないキーは、綴り違いとは限らない。将来のバージョン向けに書いた値や、
利用者が独自に置いたメモのこともある。中止すると、直しようのない理由で
ビルドが通らなくなる。警告なら CLI に出るので気づける。

有効なキーの一覧を既定値から導いたのは、表を別に持つと設定項目を増やしたときに
片方だけ更新することになるため。正しい設定に警告が出る側の誤りは、
無警告で素通りするより厄介になる。

## 検査しない場所

中身をそのまま外部ライブラリや利用者の命名に渡す場所は、pugkit が有効なキーを
知らないので検査できない。

| 場所                    | 中身                     |
| ----------------------- | ------------------------ |
| `build.html`            | js-beautify のオプション |
| `build.image.options.*` | sharp のオプション       |
| `build.image.overrides` | 利用者のファイル名       |

`build.image.options` そのものは検査する。`webpp` と書けば、その形式の設定が
まるごと無視されるため。

## 却下した案

### 旧名のキーを新しい場所へ読み替える

v1 の設定ファイルがそのまま動く。移行の手間が無くなる。

読み替えを残すと、どちらの名前も有効な状態が続く。設定ファイルを見ても
どちらが正式か分からず、新旧が混ざった設定が生まれる。破壊的変更を出せるのは
メジャーの境目だけなので、そこで断つ方が持ち越すより安い。

### 実在しないキーも中止する

「静かに壊れるより、うるさく止まる」に揃うので一貫はする。

ただし旧名と違って移行先を示せない。利用者から見ると「消せ」としか言われず、
消してよいのか判断できない。中止に見合う確からしさが無い。

### 設定に JSON Schema を持たせて検証する

型や範囲まで一度に見られる。

キーの一覧を既定値と別に持つことになり、二重管理になる。値の検証は
`imageOptimization` と `imageSourceDensity` で既に個別に入れており、
残っていた穴はキー名だけだった。穴の大きさに対して仕掛けが重い。

## 結果

v1 の設定ファイルは v2 で起動しない。移行先を並べたメッセージが出る。

実在しないキーは警告に留まるため、警告を読み飛ばす利用者には届かない。
これは意図した妥協で、中止の条件を「直し方を示せるとき」に絞った代償になる。

`config/schema.mjs` の対応表は手書きなので、移行先の綴りを間違えると
案内どおりに直しても今度は不明なキーになる。移行先が `defaultConfig` に
実在することはテストで確かめる。
