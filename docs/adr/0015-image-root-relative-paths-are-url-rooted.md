# 0015. 画像のルート相対パスはサイトルート起点で解く

## 状況

`imageInfo()` に渡すパスは、ページからの相対パス（`${Builder.dir}assets/img/hero.jpg`）か、
「/」始まりのルート相対パスのどちらかで書ける。

このうちルート相対は `src/` 直下からの参照として解いていた。
`/assets/img/hero.jpg` は `src/assets/img/hero.jpg` を指し、返る `src` は渡された文字列のまま。

`subdir` を設定した案件では、この解き方が本番で 404 になる URL を書く。
出力は `outDir/<subdir>/` に置かれ、URL にも `/<subdir>/` が入るのに、
返る `src` は `/assets/img/hero@half.webp` のまま subdir が抜けているため。
実ファイルは見つかるので警告も出ず、`width` / `height` / `srcset` も揃った状態で出力される。

リンク側は ``a(href=`${Builder.subdir}/about/`)`` と書くことになっている。
同じ書き方を `imageInfo()` にすると、今度は `src/sub/assets/img/hero.jpg` を探して
「見つからない」になり、寸法も `srcset` も付かないまま素のパスが返っていた。

つまり subdir 付きの案件では、ルート相対はどちらの書き方でも壊れていた。

## 決定

`imageInfo()` の「/」始まりのパスを、サイトルート起点の URL として解く。
subdir の前置きを外してから `src/` と `public/` に突き合わせる。

`${Builder.subdir}/assets/img/hero.jpg` がそのまま渡せるようになり、
返る `src` にも subdir が残る。subdir が空の案件では今までと同じ結果になる。

subdir を付け忘れたルート相対パスは解決しない。ただし subdir を外した位置に
実ファイルがある場合は、そうと分かる警告を出す。

前置きを外す規則は `utils/subdir.mjs` の `stripSubdir()` に置き、
dev のページ配信・幅違いのリクエスト時生成と共有する。

## 理由

`imageInfo()` が返す `src` はそのまま HTML の `src` 属性になる。
渡されたパスを解釈する側と、書き出す URL を組み立てる側が同じ文字列を扱う以上、
解釈も URL 空間で行わないと辻褄が合わない。

サイトルート起点にすると、リンクと画像が同じ書き方でそろう。
`${Builder.subdir}` を前置きするという 1 つの規則だけを覚えればよくなる。

`check` の突き合わせも同じ規則になっている（`core/check/reference-url.mjs`）。
URL を outputRoot に継ぎ足して実ファイルを探すので、subdir の抜けた `/assets/...` は
リンク切れとして報告される。参照側と検査側で解釈が違うと、
片方が通した書き方をもう片方が壊れていると言う。

付け忘れを解決しないのは、それが出力に存在しない URL だから。
実ファイルが `src/` にあることと、その URL が本番で引けることは別の話で、
見つけて寸法を返すと本番まで気づけない壊れ方に戻る。
代わりに警告で理由を伝えれば、置いてある画像を探し回らずに済む。

## 却下した案

### src/ 起点のまま、返す src に subdir を前置きする

`/assets/img/hero.jpg` と書けば正しい URL が返る。`${Builder.subdir}` を覚えなくてよく、
パスが常に `src/` の並びを写すので分かりやすい。

採らなかったのは、リンクの書き方と食い違うため。同じ「/」始まりの文字列が、
`a(href=...)` では URL、`imageInfo()` では `src/` 起点という二重の意味を持つ。
`check` も URL として解くので、検査を通すには結局 URL 空間で考えることになる。

`${Builder.subdir}` を前置きした形が二重前置きになる問題もある。
外してから前置きし直せば辻褄は合うが、`src/` に subdir と同名のディレクトリがあると
どちらの意味か決められない。

### 両方の書き方を受け付ける

前置きが有れば外し、無ければ `src/` 起点として解いて subdir を足す。
どちらで書いても動くので、移行で何も壊れない。

採らなかったのは、`src/sub/` が実在するときに解が 2 つできるため。
`/sub/assets/x.png` が `src/assets/x.png` と `src/sub/assets/x.png` のどちらを指すかは、
ファイルの有無で決まることになる。画像を 1 枚足しただけで既存ページの参照先が変わる。

前提が変われば復活しうる。`src/` 直下に subdir と同名のディレクトリを置けない、
という制約を別に設けるなら曖昧さは消える。

## 結果

破壊的変更になる。`subdir` を設定していて、かつルート相対で画像を書いていた案件では、
今まで解決していた `/assets/...` が解決しなくなる。
ただしその出力は本番で 404 になる URL だったので、壊れていたものが警告になる。

`subdir` が空の案件には影響しない。相対パスで書いている案件にも影響しない。

`src/` に `subdir` と同名のディレクトリを置いた場合、その中の画像は
`${Builder.subdir}/<subdir>/...` と 2 回重ねて参照することになる。
URL がそうなっているためで、意図した通りではあるが読みにくい。
